## Первичные находки

### R1 — P1: CMake требует заголовки по старым путям

Коммит: `0211f16`.

- `tools/generate_data.py:587` больше не копирует четыре статических заголовка
  (`goblin_map_data.hpp`, `goblin_item_icons.hpp`, `goblin_enemy_names.hpp`,
  `goblin_item_fallback.hpp`) в каталог сгенерированных данных профиля.
- Канонические заголовки теперь находятся в `src/`, но `CMakeLists.txt:105–111`
  продолжает перечислять `${GEN_DIR}/<имя>.hpp` среди исходников библиотеки.
- Сценарий: первая сборка профиля, для которого ещё нет старых копий заголовков,
  после генерации данных. Ожидается ошибка CMake об отсутствующих исходниках.
  Имеющиеся локально старые копии маскируют проблему.
- Важно для перепроверки: отсутствие заголовков в чистом клоне частично предшествовало
  этому релизу (удаление из Git в `560bc65`). Новая регрессия — прекращение копирования
  заголовков при генерации ранее не собиравшегося профиля в существующем окружении.
- Первичное направление решения: обновить пути исходников в CMake и проверить
  разрешение включений во всех профилях.

### R2 — P2: выбор поиска смешивается между персонажами

Коммит: `f7ecf80`.

- При смене слота `src/goblin_inject.cpp:2276–2281` сбрасывает фокус карты через
  `set_focus_category(-1)`, но эта функция не очищает `search::g_picks`.
- `restore_focus_pending()` в `src/goblin_inject.cpp:709` вызывает
  `search::pick_many(ids, true)`. Реализация в `src/goblin_search.cpp:300–307`
  добавляет переданные идентификаторы в существующий набор.
- Сценарий: у персонажа A выбран X, у B ранее сохранён Y; переключиться A → B,
  не открывая поиск между ними. Восстанавливается X ∪ Y, и объединённый набор
  записывается в файл фокуса B через `set_focus_rows()` / `persist_focus()`.
- Очистка устаревших выборов в `search::query()` не гарантирует очистку при смене слота:
  запрос поиска в этом сценарии не выполняется.
- Первичное направление решения: согласованно заменять состояние поиска и карты
  при восстановлении/смене персонажа, учитывая запись в файл и блокировки.

### R3 — P2: разные маркеры имеют одинаковый постоянный ключ

Коммиты: `f7ecf80`; дополнительные проявления после `cf32b5d`.

- `stable_hide_key()` в `src/goblin_inject.cpp:241–246` для `ItemLotParam_map`
  учитывает только тип и ID лота, без категории и расположения маркера.
- В текущей генерации ERR строки `2600069` (Loretta's War Sickle) и `3300015`
  (Loretta's Mastery) имеют один и тот же лот `10190`, тип `1`, без `object_name`.
- Сценарий: выбрать только оружие в поиске, сохранить и восстановить фокус.
  `restore_focus_pending()` выбирает обе строки по одному ключу. Ручное скрытие
  одной строки также распространяется на вторую.
- Даже если скрытие всей награды одного босса считать желаемым, восстановление
  индивидуального выбора поиска не должно добавлять другой предмет/категорию.
- Первичное направление решения: определить устойчивую идентичность отдельного
  маркера и формат/миграцию уже записанных ключей; не подменять их нестабильным row_id.

### R4 — P2: координаты отслеживания осколков подменяют координаты маркера

Коммит: `94f50ed`.

- `tools/generate_data.py:383–384` подставляет исходные `msb_x/msb_z` в
  `real_posX/real_posZ`, чтобы собранные осколки сопоставлялись с живым объектом.
- Но `src/goblin_inject.cpp:1214–1219` использует эти поля также как исходную
  позицию отображения; проход раздвигания маркеров повторяет это в строке 1639.
- Для перенесённых на фактическое место подбора осколков теряется поправка позиции.
  В локальных данных 22 rune pieces и один ember piece имеют расхождение > 4 единиц.
- Пример: строка `200368`, `m30_13_00_00`, `AEG099_821_9001`:
  место подбора X/Z = `(-17.718, 88.417)`, MSB = `(38.121086, 99.714676)`;
  расстояние ≈ `56.97` игровых единиц.
- Первичное направление решения: разделить исходную позицию отображения до
  раздвигания и позицию геометрии для отслеживания сбора; сохранить обе семантики.

### R5 — P2: live_loot подменяет подписи наград боссов

Коммит: `cf32b5d`.

- `boss_flag_drop_records()` в `tools/generate_loot_massedit.py:952` присваивает
  всем категориям награды первый ID из `drop['lots']`.
- Связь с лотом передаётся обычному механизму live loot. В
  `src/goblin_inject.cpp:2739–2745` название берётся из первого предмета лота,
  хотя исходный маркер может представлять другой предмет или другой лот награды.
- Сценарий без рандомайзера: Loretta's War Sickle и Loretta's Mastery получают
  лот `10190`; при `live_loot_labels=true` подпись оружия становится Loretta's Mastery.
  Этот параметр по умолчанию включён для vanilla.
- Проверена чистая функция генерации на локальных данных vanilla: 36 записей
  наград из 52 событий; в десяти случаях основной предмет записи не совпадает
  с первым предметом общего лота. Изменение категории возможно при наличии
  первого предмета в таблице иконок, но для примера с Loretta подтверждена именно подпись.
- Первичное направление решения: корректная адресация конкретной награды либо
  явное исключение агрегированных наград из неподходящего механизма live loot;
  отдельно проверить флаги исчезновения и совместимость с рандомайзером.

## Решения после двух проверок

### R1: использовать канонические заголовки в CMake

Заменить четыре `${GEN_DIR}/...hpp` в `CMakeLists.txt:105–111` на соответствующие
`src/...hpp`. Генерируемые `.cpp` и действительно генерируемые заголовки оставить
в `${GEN_DIR}`. Обновить комментарий в `CMakeLists.txt:352`.

Основной агент подтвердил, что `src/` уже присутствует в include directories
(`CMakeLists.txt:233`), а канонические заголовки уже входят в зависимости стадии
`generate_data` (`tools/build_pipeline.py:443`). Добавлять ещё один include path
или возвращать копирование заголовков не требуется. Старые локальные `.cpp` с
bare includes необходимо регенерировать, чтобы они тоже явно включали канонические
заголовки, а не соседние устаревшие копии.

Проверить после реализации: конфигурацию и сборку профиля без четырёх старых копий,
затем поддерживаемые профили; наличие старых копий не должно влиять на результат.

### R2: единое изменение фокуса и контекста персонажа

Одного вызова `clear_picks()` при смене слота недостаточно. Он вызывает применение
карты и сохранение, а уже начавшийся `apply_picks()` может иметь собственную копию
набора предыдущего персонажа.

Рекомендуемый контракт:

1. Сериализовать смену слота, изменение/восстановление фокуса и pruning общей
   транзакцией фокуса. Возможная реализация — отдельный mutex и внутренние функции,
   которые не захватывают его повторно. Порядок блокировок: mutex фокуса, затем
   mutex поиска. Защита охватывает получение набора, применение к карте и выбор
   файла для сохранения; блокировка только конечного setter не защищает от
   применения ранее скопированного набора другого персонажа.
2. Добавить операцию замены выбранных строк и внутренний сброс search state без
   reapply, callbacks в inject и файловой записи. `pick_many()` сохранить
   добавляющим для пользовательского действия «выбрать результаты».
3. Переход к category/empty focus должен согласованно очищать picks сразу,
   а не рассчитывать на побочный эффект следующего `query()`.
4. При смене слота отключить persist target, очистить старый поиск и pending restore,
   сбросить фокус карты, установить новый контекст и прочитать его сохранение.
   Восстановление выполняется заменой набора. Пока строки карты не готовы,
   держать pending state и не записывать промежуточное пустое состояние.
5. Вызовы inject/reapply и запись файлов не выполнять под `search::g_mtx`.
   Не оставлять путь, который захватывает mutex фокуса после mutex поиска.
6. Пользовательское изменение отменяет отложенное восстановление старого фокуса.
   По завершении транзакции обеспечить применение актуальной видимости и подсветки.

При перепроверке выявлены связанные ошибки того же жизненного цикла:

- `src/dllmain.cpp:918` регистрирует папку сохранений только при
  `enableManualHide=true`; `:1063` так же ограничивает синхронизацию слота.
  Фокус должен иметь папку и синхронизироваться независимо от ручного скрытия.
- `prune_focus_if_empty()` вызывается в `src/dllmain.cpp:1058`, раньше slot sync
  в `:1067`. На переходе A → B он может сбросить фокус A по флагам/собранности B
  и записать сброс в файл A. Сначала необходимо синхронизировать персонажа.
- Простое безусловное выполнение всего старого `sync_hidden_slot()` меняет
  поведение выключенного manual hide: `is_manually_hidden()` само не проверяет
  настройку. Следует отделить общий контекст/фокус от загрузки и применения hides,
  сохранив явную семантику выключенной функции.

Основной агент перепроверил эти gates, порядок вызовов и копирование набора в
`apply_picks()`. `g_applying` защищает только от одной очистки в `query()` и
не является защитой от переноса набора между слотами.

Проверить после реализации: A(X) → B(Y), переход через главное меню, B без файла,
B с category focus, неизвестные сохранённые ключи, отложенную инъекцию и
`enable_manual_hide=false`. Отдельно принудительно приостановить старый
`apply_picks()` между snapshot и применением: после смены слота он не должен
применить X к B или записать X в файл B. Проверить сохранность файла A при pruning.

### R3: отдельная идентичность маркера и версия файлов v3

Добавить только категорию к текущему ключу недостаточно. На текущих 9702 строках
ERR оба ревьюера подтвердили 24 группы с одинаковыми map-lot и category.
Например, `KeyCrystalTears`, lot `2048400021`, rows `1200041`/`1200042`:
одна tile `(61,48,40)`, но разные позиции и флаги `65320`/`2048400200`.
Astra также нашёл совпадения вне lot-ветки: отдельные `WorldHostileNPC` используют
общие флаги `7608` и `7610`.

Нужна baked идентичность источника и роли отдельного маркера, независимая от
порядкового row_id, FMG remap, live icon/category и адреса runtime loot lookup:

- Loot placement: канонический источник карты, source part/entity, вид источника
  и признак, различающий несколько записей этого источника.
- Награда босса: источник award event/flag и босс плюс стабильная baked роль
  category marker. Она не определяется изменяемым `cr.cat`.
- NPC с общим флагом: исходный NPC/part, а не только kill flag.
- Геометрия: канонический map/part. Для источников без постоянного ID допустим
  явно ограниченный позиционный fallback до раздвигания маркеров.

Переносить происхождение из генераторов отдельными полями/sidecar. Не использовать
для всех источников `object_name`: это поле уже имеет смысл в collected tracking.
Не различать точные дубликаты номером в массиве: их следует дедуплицировать либо
явно считать одним логическим маркером. Генерация должна проверять как совпадения
identity tuples, так и коллизии hashes, по всем профилям.

**Уточнение основного агента к предложению Astra:** нельзя безусловно включать
полный suffix варианта карты в идентичность. `enemy_instance_keys()`
(`tools/generate_loot_massedit.py:716`) специально считает `_00` и `_10`
одним источником, а `deduplicate()` оставляет первую запись. Идентичность нужно
канонизировать до дедупликации по известной эквивалентности источников. Variant
сохраняется, только если он обозначает самостоятельный источник. Иначе ключ
будет зависеть от того, какая запись пережила дедупликацию. Astra отдельно
согласился с этим уточнением после своего итогового отчёта.

Миграция:

1. Явные форматы `#mfg-hidden v3` и `#mfg-focus v3`, с распознаванием v1/v2/v3.
   Не считать неизвестный version header форматом v1.
2. Для нового маркера сохранить точный legacy v2 alias либо mapping old → new.
   Если R5 меняет адрес фактического лота, прежний hash нельзя вычислять из
   нового адреса. Источник/legacy identity и live locator должны быть разделены.
3. Для hidden v2 переносить старый ключ на все соответствующие новые ключи:
   это сохраняет фактическое прежнее скрытие группы маркеров.
4. Для focus v2 переносить однозначные соответствия. Неоднозначные записи
   пропускать с резервной копией исходного файла и журналом пропущенных ключей.
   **Это не миграция без потерь:** старый hash не содержит сведений, какой из
   нескольких маркеров выбрали. Произвольно выбирать один или выдавать всю группу
   за точно восстановленный пользовательский выбор нельзя.
5. V1 hide migration оставить best effort, направляя результат в новую identity.
   Выполнять миграцию после появления строк; не затирать файл пустым до разрешения
   pending state. Live text/icon metadata не считать надёжным средством снятия
   неоднозначности между версиями.

Проверить после реализации: отдельный выбор оружия Loretta; один lot/category
в разных местах; NPC с общим флагом; эквивалентные варианты карты; изменение
порядка генерации, числа соседних строк и позиции source part. Проверить, что
live labels/icons и новые loot locators не меняют ключ; проверить миграции,
резервную копию и явную обработку неоднозначных/неизвестных ключей.

### R4: две независимые пары координат

Сохранить `real_posX/Z` как MSB coordinates для geometry tracking. Добавить
обязательные `display_anchorX/Z`, которые генератор заполняет для каждой строки
из `orig_xz` после `parse_massedit_files()` и до offline de-overlap.

По цепочке `MapEntry → InjectedEntry → RowSource → CategoryRow` передавать для
отображения именно display anchor. Native positioning, live de-overlap и позиции
для hover/highlight должны получать эту пару. `data.posX/Z` оставить результатом
offline раздвигания; начинать с него ещё один live spiral нельзя. Collected tracking
продолжает использовать MSB coordinates. `(0,0)` — допустимая позиция, а не sentinel
отсутствующих данных; все новые поля обязательны в генерации всех профилей.

Основной агент отдельно вызвал читающие функции `parse_massedit_files()` и
`load_piece_metadata()` без генерации выходных файлов: у row `200368` обе нужные
пары уже присутствуют и совпадают с примером первичного ревью.

`parse_massedit_files()` применяет также смещение для Roundtable Hold
(`tools/generate_data.py:256–270`). Оно должно остаться в display anchor,
но не в tracking coordinates. Проверены rows `200077..200088`: текущая подстановка
сырых MSB координат отменяет и эту поправку отображения.

Уточнение чисел: первоначальные «22 rune + 1 ember» относятся только к записям
`rune_pieces_final.json`/`ember_pieces_final.json`, содержащим исходные MSB coordinates,
с расстоянием X/Z > 4. Это не полный подсчёт затронутых runtime markers:
дедупликация, interior transformations и spiral дают другие множества. Для проверки
исправления использовать конкретные строки и явно определённую стадию координат.

Проверить после реализации: row `200368`, Roundtable rows, обычный объект,
нулевые координаты, изменение видимости соседей и повторные de-overlap passes.
Маркер должен сохранять исходную точку отображения, tracking — находить MSB object.
Регенерировать все профили: старые aggregate initializers не должны неявно
заполнить новые координаты нулями.

### R5: точный адрес награды и отдельная политика исчезновения

Сохранить в extractor происхождение каждого award item до flatten/deduplicate:
конкретный param (`map`/`enemy`), фактическую строку lot и slot `1..8`.
Если предмет присутствует по нескольким адресам, сохранить provenance, а не терять
его при объединении. Category record получает адрес своего representative item,
то есть `items[0]` после распределения по категориям.

Провести этот locator отдельно от persistent/legacy identity через sidecar,
`MapEntry` и runtime metadata. Во всех трёх путях — injection, reapply и startup
refresh — использовать один resolver, читающий выбранный slot. Проверять диапазон
slot и наличие строки. Для item/category использовать соответствующие элементы
массивов, а не неизменные смещения первого элемента `0x00/0x20`.

Для агрегированной награды босса задать явную hide policy `BossKill`: на всех
заполненных текстовых строках остаётся исходный kill flag. `getItemFlag` одного
representative lot не означает завершение всей награды. Обычные pickup markers
продолжают использовать свою политику live pickup flags.

Сохранить anonymous mode независимо от доступности live lookup. Если нужной
строки/предмета нет, использовать baked fallback; не переходить к первому слоту
другой награды. Старый sidecar без provenance не должен молча трактоваться как
точный locator slot 1.

Дополнение Astra проверено основным агентом: таблица имён/иконок повторно читает
только исходный `items_database.json` (`tools/generate_loot_massedit.py:1483`).
В локальных vanilla данных обе награды Loretta отсутствуют и в этой базе,
и в `item_icon_table.json`. При исправлении нужно включить award items в вход
этой таблицы, сохранив существующий classifier и правила English fallback.

Граница предлагаемого исправления: сохраняется существующий контракт «один
representative marker на baked category». Адрес его предмета обновляется правильно,
но полное динамическое перераспределение всех остальных предметов агрегата после
рандомизации этим решением не реализуется и не должно обещаться.

Основной агент отверг как неполные следующие варианты:

- Исправить только `refresh_loot_from_itemlot()`: остаются два других пути slot 1.
- Обнулить `lotId/lotType`: одновременно теряются anonymous mode и прежняя identity.
- Просто исключить boss aggregates из live loot: допустимо только как явно
  ограниченный static fallback, а не сохранение поддержки live labels/icons.
- Заменить `lotId` фактической строкой и вычислять из неё прежний v2 hash:
  это ломает миграцию R3.

Проверить после реализации: Loretta, награду из нескольких lot rows, несколько
slots одной строки, комплект брони, замену representative slot рандомайзером,
отсутствующую строку/slot, переключения labels/icons/flags/anonymous в обе стороны,
исчезновение всех текстовых строк по kill flag и сохранность identity.
