# Независимая проверка runtime-находок 2.1.4

Дата: 2026-09-13. Проверка выполнена отдельным агентом Astra, Extra High.
Основа: текущие файлы рабочего дерева поверх HEAD c42bec9ac1fdafb1e31d6175d4e88ebc8bc39c23, включая уже внесённые пользователем исправления. Это не ревью только содержимого коммита HEAD.

Исходники, генераторы и три существующих документа ревью не изменялись. Игра не запускалась. Полная DLL не собиралась; собран только отдельный тест в scratch. Все процессы проверки запускались без видимых окон.

## Итог

Все пять runtime-проблем подтверждаются по существу. Для пятой нужна более узкая формулировка: при выключенной функции на старте последующее включение в меню не запускает обработчик горячей клавиши. Потеря новых скрытий через UI именно в этом сценарии исходным стендом не доказана.

| ID | Независимый вердикт | Приоритет | Что установлено |
| --- | --- | --- | --- |
| RT1 | Согласен | P1 | Достижимы конкурентные обращения к общему состоянию de-overlap; повторный ASan-запуск дал heap-use-after-free |
| RT2 | Согласен | P2 | Собранность персонажа A переносится в состояние B до положительного наблюдения живого объекта |
| RT3 | Согласен | P2 | Hover хранит старую проекцию после изменения отображаемых координат; ошибка воспроизведена также на координатах реальных строк |
| RT4 | Согласен; количественную оценку ограничиваю | P2 | Ключ Occupancy теряет area; подтверждено влияние строки m16 на положение строки m14 |
| RT5 | Частично согласен с прежней формулировкой; основной дефект подтверждён | P2 | false на старте → true в меню оставляет ручное скрытие без работающей горячей клавиши |

RT1 считаю блокером выпуска из-за подтверждённой ошибки работы с памятью на достижимом пути. Остальные пункты — конкретные ошибки поведения, требующие исправления; стенды не устанавливают частоту их проявления в обычной игровой сессии. Ни один стенд не является воспроизведением падения самой игры.

## RT1. Общий de-overlap вызывается из разных потоков

**Код.** src/goblin_inject.cpp:1769 начинает refresh_deoverlap(). Вызов меняет g_vis (:1773, :1780), координаты общих CategoryRow (:1778, :1830) и статический Occupancy (:1783). Последний содержит unordered_map<uint64_t, vector<Placed>> (:1692); соседние ячейки читаются в :1708–1710, а take() меняет их в :1741. Общей блокировки этого состояния нет.

Два независимых пути:

1. Поток игрового UI: src/goblin_maphover.cpp:897,904 → src/goblin_map_timing.cpp:244,250 → src/goblin_stall_probe.cpp:10755,10763 → v3_native_tick() (:3266) → native_marker_snapshot() (:3518, :3591, :3600) → src/goblin_inject.cpp:1870.
2. Отдельный поток, создаваемый в src/dllmain.cpp:963–966: manual_hide_hotkey_loop() (:840) → нажатие клавиши (:849) → hovered_row() (:851) → при nullptr overlay::native_hover_row() (:855) → src/goblin_overlay.cpp:2418–2424 → native_reticle_row() → обновление его snapshot в src/goblin_inject.cpp:2131 → тот же refresh_deoverlap().

**Почему сценарий достижим.** При открытой карте и курсоре над пустым местом g_hovered_row может быть nullptr: src/goblin_maphover.cpp:975, :1091. Проверка свежести hook в :1230 не означает наличия наведённого маркера. Нажатие Delete в этом состоянии всё равно доходит до построения snapshot, ещё до проверки найденного результата. На кадре периодического обновления карты старый hover-кэш может уже быть старше 200 мс: v3_native_tick() исполняется раньше вызова native_reticle_row() этого кадра. Значит, поток клавиши способен начать свой refresh одновременно с refresh карты. Достаточен штатный native-markers build, открытая карта, включённое на старте ручное скрытие и совпадение по времени; специально включать debug dump не требуется.

cache_mutex в src/goblin_inject.cpp:2109,2126 сериализует вызовы самого native_reticle_row(). Прямые вызовы snapshot из marker tick его не захватывают. Комментарий о двух потоках около :2100 и существующая блокировка устраняют прежнюю гонку hover-вектора, но не эту общую точку мутации.

**Проверка.** Тела Placed/Occupancy и refresh_deoverlap() в исходном стенде совпадают с текущим кодом. Независимый повторный запуск deoverlap_raw:

- 200 последовательных refresh после прогрева: PASS.
- Два потока после прогрева: AddressSanitizer: heap-use-after-free, чтение 4 байт в Occupancy::around; освобождение памяти vector<Placed> другим потоком в _Emplace_reallocate.

Логи: scratch/review214_runtime_independent_20260913/deoverlap_raw_serial.log и deoverlap_raw.log; сверка исходников — source_audit.txt.

В deoverlap_raw отключена только аннотация границ STL vector (_DISABLE_VECTOR_ANNOTATION), сам AddressSanitizer включён. Поэтому полученная ошибка не сводится к прежнему сообщению bad-__sanitizer_annotate_contiguous_container. Вид ошибки может различаться между прогонами: ранее основной агент получил heap-buffer-overflow, независимый прогон — use-after-free.

**Границы.** Стенд подменяет проверку видимости постоянным true, исключает engine API и запускает два refresh через барьер. Он намеренно повышает вероятность пересечения и не моделирует частоту нажатий или игровой планировщик. Общие контейнеры и алгоритм размещения сохранены; возможность такого пересечения установлена отдельно по реальным вызывающим функциям. Повреждение памяти игры не наблюдалось.

**Предлагаемое исправление.** Минимальное — одна общая блокировка расчёта и чтения его результата: refresh вместе с копированием snapshot, чтение в focus_highlight_points() (:961) и display_position() (:949). Только mutex внутри refresh недостаточен: другой вызов сможет начать менять результат, пока первый строит snapshot. Только thread_local Occupancy тоже недостаточен: общими останутся g_vis и координаты.

Следует разделить внешние блокирующие функции и внутренние функции, вызываемые с уже захваченным mutex. native_marker_snapshot() вызывает focus_highlight_points() (:1914); повторное захватывание обычного mutex здесь создаст deadlock. При сохранении hover-cache mutex зафиксировать единый порядок его захвата относительно layout mutex. Более крупный вариант — рассчитывать layout одним владельцем и публиковать неизменяемый snapshot для остальных потоков. Это исправление не следует объявлять решением всех иных гонок конфигурации/фокуса без отдельного аудита их писателей.

**Проверки после правки.** Повторить serial/concurrent стенд; добавить конкурентное получение snapshot и highlight/display positions с проверкой согласованности координат и размера g_vis. Проверить открытие/смену слоя и отсутствие deadlock на вложенном пути snapshot → focus highlights. В игре отдельно нажать hide над пустой картой во время обновления.

## RT2. История collected не ограничена персонажем

**Код.** g_collected_rows очищается в src/goblin_collected.cpp:631, при инициализации, вызываемой из src/dllmain.cpp:923. В рабочем цикле refresh() не отслеживает слот или поколение персонажа. Когда оба manager pointer отсутствуют, :783–784 просто возвращает 0. При появлении новых данных :961–967 переносит старые строки в new_collected, если их живой объект не обнаружен в текущем WGM. Отсутствие старого подбора в GEOF B не отменяет перенос.

sync_hidden_slot() (src/goblin_inject.cpp:2450) занимается hidden/focus, но не collected. В watcher новый collected refresh исполняется в src/dllmain.cpp:1009, а slot sync — только в :1066. Переставленный перед pruning slot sync исправляет прежний последовательный дефект фокуса, но не очищает collected.

**Сценарий.** A собирает отслеживаемый объект X. Затем игрок загружает B в другой локации; B ещё не собирал X. Его GEOF не содержит записи X, а WGM не содержит живой X, поскольку место не загружено. Старая отметка A сохраняется у B, в том числе после следующих refresh. Посещение живого X позволяет снять её.

**Проверка.** В collected_harness.cpp сохранено целое тело текущего refresh(). Подменены чтение GEOF/WGM и доступ к памяти параметра. Независимый запуск дал:

    A collected row: collected=1 marker_area=99
    B fresh data, distant tile: collected=1 marker_area=99 (expected 0 / 60)
    B visits live object: collected=0 marker_area=60

Лог: scratch/review214_runtime_independent_20260913/collected_harness.log.

**Последствия, проверенные по коду.** Native-маркер скрывается через native_row_hidden() (src/goblin_inject.cpp:1618). Поиск с фильтром использует hidden_marker_original_ids() (:1001) → row_is_hidden() (:383) → collected; применение фильтра находится в src/goblin_search.cpp:199–206. Прогресс также читает collected через src/goblin_progress.cpp:253–255.

Возможна и потеря сохранённого фокуса B: если весь восстановленный набор B состоит из таких ошибочно собранных строк, после восстановления (src/goblin_inject.cpp:2513–2514) prune_focus_if_empty() (:1019–1032, вызов в src/dllmain.cpp:1075) считает его пустым. set_focus_category(-1) вызывает persist_focus() (src/goblin_inject.cpp:678), который перезаписывает уже файл B (:740–756). Это отдельный достижимый сценарий по коду; запись файла через полную цепочку collected → slot sync → pruning данным стендом не исполнялась. Здесь не утверждается повреждение игровых save-файлов: затронут собственный файл фокуса мода.

**Границы.** Стенд моделирует смену данных персонажа, а не вызывает игровой загрузчик; manager pointers и содержимое snapshots задаются вручную. Для установленного дефекта не требуется, чтобы pointers обязательно обнулялись при загрузке: при прямой замене данных carry-forward также сохраняет X.

**Предлагаемое исправление.** Ввести границу персонажа/поколения перед чтением и публикацией collected в watcher. При её смене отменять старую историю, восстанавливать изменённые areaNo, сбрасывать счётчики и явно уведомлять видимость. Первый snapshot нового персонажа не должен наследовать набор предыдущего; pruning/сохранение фокуса должны видеть состояние нужного персонажа. При неготовых данных нельзя на основании переходного состояния уничтожать восстановленный фокус.

Недостаточно просто вызвать g_collected_rows.clear(): при пустом новом наборе равенство в src/goblin_collected.cpp:1032 сразу завершит refresh и пропустит восстановление старых areaNo из :1055–1058. Нельзя также рассчитывать только на изменение количества: разные наборы могут иметь одинаковую мощность, тогда проверка src/dllmain.cpp:1051 не обновит видимость. Нужны явный reset/changed/epoch и согласованное применение. Сбрасывать следует динамическое состояние сбора, сохраняя таблицы отслеживания, remap ID и зарегистрированные адреса; повторный полный initialize() после remap не является безопасной заменой такой операции. Новый reset должен исполняться тем же владельцем, что refresh, либо быть защищён от завершения старого refresh после сброса.

**Проверки после правки.** A(X) → B без X, включая B в другой локации; переход через главное меню и прямую замену данных; новый пустой набор; замена на набор того же размера; восстановление original areaNo; сохранённый фокус B на X; возвращение к A. Для одного персонажа сохранить нужный carry-forward при обычной разгрузке локации.

## RT3. Hover навсегда запоминает первую проекцию строки

**Код.** src/goblin_inject.cpp:2125 хранит projected по одному original_row_id. Обновление snapshot в :2131 не обновляет его уже существующие элементы: :2136 их пропускает, :2140 только добавляет новые. Последующий поиск использует эти старые (mx,mz) (:2152–2158). Между тем refresh_deoverlap() меняет native_px/native_pz при изменении видимого набора.

Реальный маркер перемещается: src/goblin_stall_probe.cpp:3148–3157 передаёт актуальные координаты snapshot в to_map() и v3_native_move(). Комментарии о неизменных позициях около src/goblin_inject.cpp:2099,2113–2124 больше не соответствуют этому поведению.

**Почему стенд применим.** Исходный hover-стенд возвращает также невидимую строку A. Это соответствует production: native_marker_snapshot() в src/goblin_inject.cpp:1877–1884 возвращает подходящие base rows независимо от visible; include_hidden не является фильтром отдельных строк. Поэтому первая проекция невидимой A действительно может попасть в projected. Обычный невидимый сосед не занимает место в Occupancy; после включения он может вытеснить B.

В native_reticle_row() нет повторного выбора по текущим координатам после чтения projected. Его результат используется в src/goblin_maphover.cpp:1013–1067 для текста и публикации наведённой строки; hotkey берёт эту строку либо вызывает тот же поиск. Сравнение с настоящим engine pin может маскировать симптом рядом с таким pin, но при отсутствии engine item ветка :1022–1024 принимает наш результат.

**Проверка на реальных строках.** Дополнительно создан и собран scratch/review214_runtime_independent_20260913/real_pair_harness.cpp. В нём неизменны тела Occupancy, refresh и hover-функции, а линейная проекция для area 60 использует точные формулы src/goblin_mapproject.cpp:80–84, включая константы 7040 и 16512.

В ERR найдены две строки на одном display anchor:

- 4600007, LootReusables, src/generated/goblin_map_data.cpp:68211;
- 5300247, LootSmithingStonesLow, src/generated/goblin_map_data.cpp:78558.

Обе: area 60, grid 37/42, layer 0, display_pos=(64.695,-129.378). В исходной baked data у второй posZ уже раздвинут; runtime anchor берётся именно из display_pos, через src/goblin_inject.cpp:1143,1353–1354. У обеих один disable flag 1037427900; обе могут одновременно оставаться несобранными, а категории можно включать раздельно.

Сначала A скрыта, B видна; после заполнения кэша A включается. B перемещается в (64.695,-137.378). После ожидания 250 мс и наведения на новую позицию B результат — A (4600007), ожидаемый B — 5300247. Лог real_pair_harness.log. Исходный синтетический hover-стенд также повторно дал actual 11 вместо 22.

**Границы.** Применимость проверена для native markers на overworld, где проекция вычисляется без engine converter. Видимость категорий, reticle и строки параметров в стенде заданы заглушками; запуск игрового tooltip не выполнялся. Это устойчиво устаревшая проекция, а не только допустимое отставание visibility на 200 мс. Масштаб может изменить проявление на «нет hover» вместо «выбран сосед».

**Предлагаемое исправление.** Хранить вместе с результатом полный вход проекции (area,gx,gz,px,pz) и пересчитывать при его изменении; либо пересчитывать все элементы обновлённого snapshot, используя уже существующий memo в mapproject::to_map() (src/goblin_mapproject.cpp:98–176). Его key включает координаты, а не только ID строки. Нельзя использовать старый результат после изменения входа, если новая проекция временно недоступна: такой кандидат должен ждать успешной проекции. Учесть смену поколения данных и не возвращать многотысячные engine conversions на каждый кадр.

**Проверки после правки.** Скрытый → видимый сосед, обратное выключение, сбор соседа, переключение фокуса, смена слоя/повторное открытие карты. Проверить точку reticle непосредственно на отображаемом B при нескольких zoom. Для dungeon отдельно проверить повторную проекцию и поведение при временно недоступном converter.

## RT4. Ключ Occupancy теряет карту

**Код и арифметика.** tile формируется как (area << 40) | (gx << 20) | gz (src/goblin_inject.cpp:1808–1809, аналогично :1797). В Occupancy::key() (:1694–1697) он снова сдвигается на 26. Биты area оказываются выше 63 и полностью теряются в uint64_t. Это потеря данных при допустимых unsigned-сдвигах, а не отдельный неопределённый сдвиг на 66.

Следовательно, при одинаковых gx/gz и координатах ячейки разные area дают одинаковый ключ. Placed (:1684–1688) не хранит карту и не позволяет отфильтровать такое совпадение после lookup. Локальные координаты разных карт ошибочно сравниваются друг с другом. Разные слои сами по себе не доказывают дефект: native_row_visible() фильтрует слой, поэтому для примера нужны карты одного слоя.

**Проверка.** Символьный пример m10/m11 из исходного стенда повторился. Дополнительно проверены полные записи двух реальных пар:

| Профиль | Первая строка | Вторая строка | Общие поля |
| --- | --- | --- | --- |
| ERR | 4900001, area 16, LootMPFingers, display (10.655,-82.987) | 5500037, area 14, LootConsumables, display (10.216,-82.477) | gx=0, gz=0, layer=0 |
| vanilla | 4900015, те же поля первой строки | 5500032, те же поля второй строки | gx=0, gz=0, layer=0 |

Источники: src/generated/goblin_map_data.cpp:72214,85208; src/generated_vanilla/goblin_map_data.cpp:40781,54175. Поля записаны в scratch/review214_runtime_independent_20260913/real_data_pair.json. Для этих конкретных строк tracking и display совпадают; использован именно display. Расстояние локальных anchors ≈ 0.67292, меньше 8.

В отдельном тесте с двумя видимыми ERR-строками area 14 получает (10.655,-90.987) вместо собственного (10.216,-82.477). После скрытия строки area 16 маркер area 14 возвращается в свой anchor. Лог — real_pair_harness.log. Таким образом, подтверждена не только коллизия числа, но и неправильное размещение реальных данных.

Обе строки имеют ненулевые иконки и отдельные pickup disable flags; при несобранных предметах, разрешённых категориях и открытых необходимых gates одновременная видимость допустима. Поскольку проверка видимости не отсекает другую area того же слоя, удалённая карта продолжает участвовать в Occupancy. Стенд изолирует две строки; дополнительные видимые маркеры/зажжённые благодати в полной игре могут изменить точное итоговое смещение.

**Уточнение количества.** Числа 402 для ERR и 246 для vanilla из предварительного анализа — не число реально сдвинутых маркеров. Предварительный parser выдаёт real_pos, тогда как runtime использует display_pos; ещё требуются actual visibility, порядок размещения и резервирование благодатей. Для вердикта эти количества не использованы. Независимо подтверждены приведённые пары и механизм.

**Предлагаемое исправление.** Использовать составной ключ {tile,cx,cz} с полным operator== и отдельным hasher; либо хранить такую полную идентичность в bucket и проверять её при чтении. Простая замена текущей упаковки на иной 64-битный hash как единственную идентичность не даёт строгой изоляции карт. Коллизии hasher допустимы, если unordered_map сравнивает полный ключ.

**Проверки после правки.** Одинаковые локальные anchors в разных area не взаимодействуют; те же anchors в одной карте раздвигаются. Проверить отрицательные cx/cz, соседние ячейки и размещение рядом с зажжённой благодатью. Повторить реальные пары; отдельно оценивать полный набор по display anchors и реальному состоянию видимости.

## RT5. Включение ручного скрытия после старта не запускает worker

**Код.** manual_hide_hotkey_loop() создаётся только под стартовым if (enableManualHide) в src/dllmain.cpp:963–966. Внутри уже работающего потока настройка проверяется повторно (:846), поэтому true → false → true при работающем worker — другой сценарий.

Настройка доступна в меню, а не только в ini: src/goblin_config_schema.cpp:353–354; явный checkbox меняет target в src/goblin_overlay.cpp:1077–1084, вызывает reapply_live_settings() (:1133–1134) и сразу открывает содержимое вкладки (:1137–1142). В native menu этот ключ также перечислен в src/goblin_native_menu.cpp:563. reapply_live_settings() (src/goblin_inject.cpp:2684–2696) потоки не запускает.

**Достижимый сценарий.** Запустить мод с enable_manual_hide=false, загрузить персонажа, включить функцию в меню и попытаться скрыть маркер клавишей. Worker не существует, поэтому действие не исполняется; переключение персонажа также не создаёт поток. Проверка сделана по коду, без инъекции клавиш в игру.

**Связанная проблема состояния.** При первом slot sync с выключенной функцией g_hidden_file остаётся пустым (src/goblin_inject.cpp:2489–2510). Последующий sync того же слота выполняет только миграцию/pending focus (:2453–2467), не устанавливая файл и не загружая сохранённые скрытия после включения. Это важно для исправления worker: одного безусловного запуска потока недостаточно для правильного восстановления и сохранения скрытий.

**Что исходный стенд не доказывает.** Старый state_harness.cpp вручную вставляет запись в g_manual_hidden после включения. Поэтому его строка «new hide is lost on reload» доказывает поведение пустой цели записи при искусственно добавленной записи, но не достижение этой вставки через пользовательский hotkey в сценарии false на старте. В этом сценарии hotkey до вставки вообще не дойдёт. Такое утверждение о потере новых UI-скрытий снимаю; не считаю его отдельным подтверждённым дефектом этого сценария.

**Предлагаемое исправление.** Запускать единственный worker независимо от начального значения, оставив проверку включённости в цикле, либо создавать его через идемпотентный ensure-start при включении. Одновременно обрабатывать переход feature-state в текущем слоте: загрузка hidden-набора, правильный persist target и применение видимости. При этом не сбрасывать восстановленный search/category focus и не перезаписывать файлы неподдерживаемых версий. Более ограниченный продуктовый вариант — явно перевести опцию в режим «после перезапуска», убрав обещание немедленного изменения из меню; текущий UI такого ограничения не сообщает.

**Проверки после правки.** false на старте → true в каждом поддержанном меню; загрузка существующего hidden-файла, новое скрытие и сохранение, отсутствие файла, same-slot toggle, смена персонажа с выключенной функцией, true → false → true, отсутствие второго worker и защита неизвестных версий файлов.

## Ранее упомянутые пункты

### OLD1. Старый apply_picks может перезаписать фокус нового слота — согласен, P2

Это не уже исправленное окно между публикацией picks и поднятием g_applying, описанное как F1 в старом followup. Текущее g_applying повышается под g_mtx (src/goblin_search.cpp:307–309, :328–331); эта правка присутствует.

Оставшееся окно находится позже: apply_picks() копирует набор под mutex (src/goblin_search.cpp:289–291), затем отпускает его и вызывает set_focus_rows(p) (:298). Смена слота делает forget_picks() (src/goblin_inject.cpp:2484), устанавливает файл B и восстанавливает его выбор (:2512–2514), но не отменяет уже скопированный p от A. Проснувшийся старый apply меняет карту и вызывает сохранение (:684–698) уже в текущий файл B. Счётчик g_applying не проверяет ни поколение слота, ни актуальность снимка.

Независимо повторно запущен scratch/review214_20260913/harness_build/Debug/state_harness.exe в отдельном scratch/.../state_run. Лог scratch/review214_runtime_independent_20260913/state_harness.log:

    REPRODUCED: search set is B (202), map and B file contain A (101 / key 1001), applying=0

Сверены используемые текущие setters, persist, mutators и apply (state_source_audit.txt). В apply вставлен единственный тестовый барьер после получения снимка. Переключение персонажа моделируется последовательностью операций смены цели записи/очистки/восстановления; реальный игровой active_save_slot не используется для этого теста. Барьер выбирает допустимый порядок потоков; он не добавляет возможность записи, которой нет в production. Пользовательское изменение поиска исполняется из ImGui (src/goblin_overlay.cpp:1039) независимо от watcher; достаточно задержанного apply при смене персонажа. Частота такого окна не измерена.

Предлагаемое исправление: транзакция применения выбора и смены его контекста либо проверка поколения с атомарным относительно slot switch commit. Одна проверка generation до незаблокированного setter недостаточна — между ней и записью снова возможна смена слота. Нужно защищать применение к карте и выбор файла, а также запрещать применение более старой редакции в том же слоте. Не переносить calls в inject под существующий search mutex без аудита порядка блокировок и обратных вызовов. Проверить A → B с задержанным apply, две конкурирующие правки одного слота и сохранение только актуального набора.

### OLD2. build.bat пропускает generate_menu_icon_tags.py — согласен, P2

build.bat:190–206 (:gen_shared) вызывает logo, map icons, overlay icons и i18n, но не generate_menu_icon_tags.py. В tools/build_all.py:75–76 этот генератор присутствует и вызывается в :145–151. src/goblin_own_movie.cpp:11 безусловно включает его результат generated_shared/goblin_menu_icon_tags.hpp; сам путь результата задан в tools/generate_menu_icon_tags.py:49.

Поиск по CMake, pipeline и остальным tools не обнаружил альтернативного вызова этого генератора на пути одиночного build.bat. Поэтому после изменения его входов одиночная сборка может использовать старый заголовок; при отсутствии заголовка этот путь не создаёт необходимый include. Наличие уже сгенерированного файла или предварительный запуск build_all маскируют дефект. Это не означает, что текущая локальная DLL обязательно собрана со старым содержимым: происхождение её артефактов не проверялось.

Предлагаемое исправление: включить шаг в :gen_shared в согласованном порядке зависимостей и с проверкой exit code; предпочтительно общий список/входной shared-stage для обоих способов сборки. Проверка — изолированная сборочная копия без этого артефакта и изменение входа генератора с последующим одиночным build. Production-generators и build.bat в этом ревью не запускались.

## Уточнённые и отклонённые утверждения

- Исправленные R1/R4 и F1/F2/F3 из прежних документов не предъявляются заново как новые runtime-дефекты. OLD1 — другое окно после снятия search mutex; RT2 — несброшенная collected history, а не уже исправленный последовательный union picks.
- «Hover cache защищён, значит de-overlap однопоточен» — неверно для прямых snapshot из map tick.
- «Два вызова из самого map frame образуют гонку» — неверная аргументация: они последовательны. RT1 опирается на отдельный worker.
- «ASan доказывает падение игры» — неверно: он доказывает ошибку памяти вынесенного алгоритма, применимость которого установлена по коду.
- «Позиции строк неизменны весь сеанс» — неверно для runtime de-overlap; 200-мс обновление snapshot не обновляет projected.
- «402/246 — столько маркеров реально сдвинуто» — не установлено. Требуются display anchors и полное состояние visibility/layout.
- «При false на старте можно через hotkey создать новое скрытие и потерять его» — данным путём невозможно до устранения отсутствующего worker. Искусственная вставка в map стенда не заменяет пользовательское действие.
- Перенос collected не является записью в игровые сохранения. Доказаны собственное состояние мода и возможная перезапись его focus-файла.
